## 先说结论：一份好 issue 长什么样

四件事说清楚就够了：**在哪出的、怎么复现、期望什么、实际什么**，再加上版本与环境。
维护者最怕的不是问题多，而是「用了就是不行」——这种描述没法动手，只能来回问。

提 issue 的入口：<https://github.com/sywdn-001/AutoOps/issues/new/choose>（点「New issue」会看到三个表单）。

## 第一步：提之前先花 30 秒

- **搜已有 issue（含已关闭）**：用报错原文里的英文单词搜，比用中文描述命中率高得多。
- **翻一眼文档**，很多「这是 bug 还是就这么设计的」在这里就有答案：

| 你的情况 | 先看哪份 |
| --- | --- |
| 不知道怎么上手 | [图文教程](图文教程.md) |
| 某个页面、按钮是什么意思 | [使用手册](使用手册.md) |
| 装不上、端口被占、密钥怎么配 | 根 [README](../README.md) 的「快速开始 / 部署到生产」 |
| 想知道为什么这么设计 | [需求对照](需求对照.md)、[审计与安全](审计与安全.md) |
| 想知道这个现象是不是已知的 | [验证记录](验证记录.md)（里面记着踩过的坑） |

- 确认一下你跑的是不是最新代码：`git rev-parse --short HEAD` 和仓库 main 对一下。

## 第二步：选对模板

| 模板 | 什么时候用 | 必填项 |
| --- | --- | --- |
| 🐞 **Bug 报告** | 有东西坏了，或者行为和文档不一致 | 版本、环境、复现步骤、期望 vs 实际 |
| 💡 **功能建议** | 希望增加或改变某个能力 | 使用场景、现在有多麻烦、期望的用法 |
| ❓ **使用提问** | 照着文档做还是卡住了 | 想做什么、卡在哪一步、已经读过哪份文档 |

表单里标了「必填」的项请别删——那是判断「能不能复现」的最小信息集。
**安全漏洞不要用这三种模板**，见本文最后一节。

## 第三步：标题怎么写

- 推荐 `[模块] 现象`，例如 `[网页终端] WinRM 会话里 cls 没有清屏`、`[SSH 网关] 登录后主机菜单没有列出我的授权主机`。
- 一句话说现象，不要把整段报错堆在标题里。
- 「救命」「急」「进来看看」这种标题信息量为零，反而会更慢。

## 第四步：版本与环境（把命令输出贴进来就行）

```bash
cd bastion-backend
git rev-parse --short HEAD                    # 你跑的版本
python -V                                     # 后端 Python 版本
curl -s http://127.0.0.1:5000/api/health      # 服务是否启用了网关等
```

前端再补三条：浏览器与版本、`node -v`、你是 `npm run dev` 还是用后端挂的 `dist/`
（这两种情况下「界面没更新」的表现完全不同）。

被管主机也要写清：`Ubuntu 22.04 / ssh:22`、`Windows Server 2025 / winrm:5985 + rdp:3389` 这样。

## 第五步：复现步骤写到「别人照着做也能看到同样结果」

- **从登录开始编号**，不要跳步：`1. admin 登录后台 → 2. 打开「资产管理 / 主机列表」 → 3. 在 win-75 行内点「编辑」 → 4. …`
- 必现就写「必现」；只见过一两次就写「偶发，约 2/10 次」——**这个数字对定位很有用**，别省。
- 如果你已经缩小到某个条件（只在 Edge 上、只有 WinRM 主机、只有中文主机名会出），一定写进去，那是含金量最高的部分。

## 第六步：证据（截图 / 日志 / 审计 id）

- **界面问题**：截图直接拖进输入框，最好把出问题的那一条圈出来。
- **接口问题**：F12 → Network 里那条请求的 URL、状态码、响应 JSON；Console 里的红色报错原文。
- **后端问题**：启动服务那个终端的输出，从报错往前多贴二三十行。
- **「谁在什么时候连了哪台机」这类问题**：审计中心里那条记录的 id、时间、动作（`action`）——比任何文字描述都管用。
- 贴日志时**不要贴密钥**（`BASTION_SECRET_KEY` / `BASTION_JWT_SECRET` / `BASTION_FERNET_KEY`）和资产口令，脱敏后再贴。

## 第七步：提交前对着这张清单过一遍

- [ ] 我搜过 issue（含已关闭），这不是重复的
- [ ] 我跑的是 main 上最新的代码（或者写清我用的是哪个 tag/commit）
- [ ] 复现步骤从登录开始，别人照着做能重现
- [ ] 我写了「期望发生什么」和「实际发生了什么」
- [ ] 我贴了报错原文 / 日志 / 截图，不是「反正就是不行」
- [ ] 我写了环境：Python、Node 或浏览器、堡垒机所在系统、被管主机系统与协议端点
- [ ] 我没有在 issue 里泄漏任何密钥或口令

## 第八步：提完之后

- 维护者会打标签（`bug` / `enhancement` / `question`）并可能追问细节；**issue 不会被删**，它会成为这条问题的上下文。
- 自己找到了原因就**直接跟帖**说明，哪怕结论是「是我用错了，不是 bug」——这种澄清比默默关掉有价值得多。
- 想自己动手改：见根 [README](../README.md) 的「贡献指南」（提交信息格式、提交前必须跑的门禁）。

## 可能被追问的点，提前答掉

| 会被问 | 提前怎么答 |
| --- | --- |
| 你的版本？ | `git rev-parse --short HEAD` |
| 改过配置吗？ | 列出设过的 `BASTION_*` 环境变量名（**不要贴值**） |
| 后端日志呢？ | 跑服务那个终端的完整报错段 |
| 换个浏览器 / 换台主机还这样吗？ | 试过就写结论，没试过就直说没试 |
| 审计里有记录吗？ | 贴审计中心那条记录的 id 与 `action` |
| 是前端还是后端的问题？ | F12 → Network 看那条请求是 4xx/5xx（后端）还是请求根本没发出去（前端） |

## 三件不要开公开 issue 的事

- **安全漏洞**（越权、密钥泄漏、命令注入、审计被绕过…）：请用仓库 **Security** 面板里的
  「Report a vulnerability」（看不到该入口就私信维护者），**不要在公开 issue 里贴细节与利用步骤**；
  支持的版本、范围界定、处理时限与安全港写在同一份 [SECURITY.md](../SECURITY.md) 里。
- **已经能自己修的**：直接提 PR 更受欢迎，PR 说明里写上「修的哪个 issue」。
- **没有任何复现信息的问题**：会被要求补充；补不上就只能关掉，这不是不欢迎，而是没法动手。

## 最后一句

提 issue 是帮忙，不是添麻烦。你把「怎么复现」写清楚，这个项目就少一个坑——谢谢。
